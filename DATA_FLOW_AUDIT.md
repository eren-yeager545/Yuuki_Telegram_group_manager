# Personal Data Flow Audit

## Scope

This audit covers the current cleaned Telegram bot repository and maps where user-related data enters, where it is stored, where it is transmitted, and what was changed to reduce unnecessary exposure.

## What personal data enters the app

### Telegram platform data received from updates

The bot receives user and chat metadata from Telegram updates, including:
- User ID
- Full name
- Username
- Chat ID
- Chat title
- Chat username
- Message text and captions
- Contact payloads when a Telegram contact message is posted
- Member join/leave events

### User-generated content processed by commands

The bot also receives:
- Notes content saved by admins
- Filter trigger words and replies
- Blacklist words or phrases
- Reported message context
- Welcome and goodbye templates
- Quiz answers entered in chat

## Data collection points and flow

| Entry point | Data collected | Where it goes next | Stored? | Sent externally? |
|---|---|---|---|---|
| `wrapped_start()` in `bot.py` | User full name, username, user ID from Telegram update | Previously sent to logs; now reduced to a redacted operational log | Not directly stored here | May be sent to log channel as redacted text |
| `message_router()` in `bot.py` | User ID, full name, username, chat ID, chat title, chat username, message text/caption, contact presence | Used for notes, filters, locks, flood control, blacklist matching, quiz answer checking, and DB upsert helpers | Yes, selected metadata stored in SQLite | No third-party transfer besides Telegram API actions |
| `service_router()` in `bot.py` | New member profile data, leaving member profile data | Used to render welcome/goodbye messages and optional temporary mute | Not directly persisted by this function | Sent back into Telegram chat as welcome/goodbye message |
| Admin commands in `handlers/admin.py` | Notes, filters, blacklists, welcome text, rules, fed actions, moderation targets | Passed to store layer and moderation actions | Yes, command-driven settings stored in SQLite | No external third-party API found |
| Common commands in `handlers/common.py` | User requests such as rules/help/privacy and note lookups | Rendered back into Telegram chat | Minimal/no new storage | No external third-party API found |

## Storage map

The app uses local SQLite storage (`bot.db`) through functions in `data/store.py`. Based on the repository structure and command set, stored data includes:
- User records: user ID, full name, username, seen timestamps
- Group records: chat ID, title, username, seen timestamps
- Notes and button-note payloads
- Filters and blacklist entries
- Warn counts and moderation actions
- Reports settings and moderation logs
- Federation metadata, federation memberships, fed admins, fed bans
- Temporary action records for timed mute/ban expiry
- Welcome/goodbye/rules settings

No password storage flow was found in this repository. No signup, login, or password collection feature exists in the current app snapshot.

## External data transfers

### Telegram Bot API

This is the primary external service. User-related data leaves the app only when the bot uses Telegram methods such as:
- `send_message`
- `reply_text`
- `restrict_chat_member`
- `ban_chat_member`
- `unban_chat_member`
- `delete_message`
- `get_chat_member`

Data sent to Telegram includes chat IDs, user IDs, message text generated by the bot, and moderation instructions.

### Log channel forwarding

If `LOG_CHANNEL_ID` is configured, some operational messages are forwarded to a Telegram log channel. This is still a Telegram transfer, not a separate third-party analytics or monitoring SDK.

### Other third parties

No Supabase, Stripe, MongoDB, PostgreSQL, OAuth provider, analytics SDK, Twilio, SendGrid, OpenAI, Firebase, or AWS integration was found in the current cleaned repository snapshot.

## Logging audit and fixes

### What was found

The codebase uses Python logging in `bot.py` and sends some events through `log_event()`. The most important personal-data exposure found was:
- Startup log previously included full name, username, and numeric user ID of the user who started the bot.
- Quiz delivery logs previously included chat title and chat ID.

### What was fixed

These logs were minimized and replaced with redacted operational messages:
- `Bot started by an authorized user [REDACTED]`
- `Quiz #<id> sent to a configured group [REDACTED]`

### Remaining logging risk

Moderation and operational logs may still include internal Telegram numeric IDs where the store layer records admin actions. These IDs are not credentials, but they are still personal or account-linked identifiers and should be treated carefully if log data is exported or shared.

## Password handling

No password collection, password storage, or password verification flow exists in the current app. Therefore:
- No plaintext password handling was found
- No hashing implementation was required for the current feature set
- If authentication is added later, use bcrypt, argon2, or scrypt only

## Cookies and browser storage

This repository is not a web app and does not implement browser cookies, localStorage, or sessionStorage. No cookie flags or browser storage risks were found in the current app snapshot.

## API response filtering

This bot does not expose a REST or GraphQL API in the current repository. Responses are Telegram bot messages. The main response-exposure risks are therefore:
- Returning more user detail than needed in command replies
- Showing moderation history or report data too broadly inside chats

No password hashes or web API payloads were found. Still, moderation/admin commands should continue to avoid dumping full user tables or unnecessary identifiers into public chats.

## Complete map

| Data type | Where collected | Where stored | Where sent | Notes |
|---|---|---|---|---|
| Telegram user ID | Telegram updates in `bot.py` | SQLite via store helpers | Telegram moderation API calls, optional log channel text | Needed for moderation and identity tracking |
| Full name | Telegram updates in `bot.py` | SQLite via user upsert | Welcome/goodbye rendering, possible note templates | Reduced from startup logs |
| Username | Telegram updates in `bot.py` | SQLite via user upsert | Welcome/goodbye rendering | Reduced from startup logs |
| Chat ID | Telegram updates in `bot.py` | SQLite via group upsert | Telegram send/restrict/ban/delete calls | Reduced from quiz logs |
| Chat title | Telegram updates in `bot.py` | SQLite via group upsert | Previously in quiz log text | Reduced from logs |
| Message text/caption | `message_router()` | Processed in memory; may be stored indirectly in notes/filters/blacklists if admins save content | Telegram replies when matched or moderated | Core content-processing path |
| Contact message payload presence | `message_router()` via `msg.contact` | Not clearly stored by default | Used to trigger contact locks | Sensitive category; avoid logging |
| Notes/filter/blacklist content | Admin commands | SQLite | Replayed into Telegram chats when triggered | Admin-entered content can include PII if admins type it |
| Welcome/goodbye templates | Admin commands | SQLite | Telegram chat messages | Can reveal usernames/full names by design |
| Reports/moderation metadata | Admin actions | SQLite | Telegram admin/log outputs | Keep visibility limited to admins |

## Recommended next hardening steps

1. Minimize stored profile fields if full names and usernames are not required long term.
2. Review `data/store.py` functions for retention limits and add deletion/cleanup policies for stale user and group records.
3. Restrict admin-only output commands so warned lists, modlogs, reports, and federation data never appear to normal users.
4. If exporting logs or DB backups, treat Telegram numeric IDs and usernames as personal data.
5. Remove duplicate documentation copies under the repo `output/` folder to reduce accidental spread of audit documents.
